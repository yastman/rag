# Issue #1401 — furniture/furnished schema reconciliation review (v1)

The document/CSV Qdrant lane (`gdrive_documents_bge[_scalar|_binary]`) had a three-way schema drift: the chunker wrote `metadata.furnished` BOOL, the index setup script created a `metadata.furniture` KEYWORD, and the runtime filter producers (FilterExtractor, QueryAnalyzer SYSTEM_PROMPT, query_filter_signal) emitted `furniture: "Есть"` against the never-populated keyword field — so any furniture filter on this lane silently dropped. The fix retires the dead keyword, makes `metadata.furnished` BOOL the single canonical for the lane, aligns the three runtime producers, adds two regression tests plus a migration paragraph in `docs/QDRANT_STACK.md`, and leaves the apartments lane (top-level `is_furnished` BOOL) untouched. The bool flow through `qdrant._build_filter` was verified live: `{"furnished": True}` produces `FieldCondition(key="metadata.furnished", match=MatchValue(value=True))`.

**Watch for:**
- *(likely)* `QueryAnalyzer` is loaded via `get_prompt_with_object("query-analysis", fallback=SYSTEM_PROMPT)` — the SYSTEM_PROMPT change only governs the fallback. The live prompt sits in Langfuse and the PR does not update it.
- *(likely)* With the index now BOOL, an LLM that emits `"furnished": "true"` (string) silently produces zero hits; the old keyword index was tolerant of this drift, the new one is not. `QueryAnalysisResult.filters` is `dict[str, Any]` so there is no value-level coercion.
- *(confirmed)* The script's `if "already exists" in str(e).lower()` branch increments `success_count` on any pre-existing index regardless of its actual schema — fine for the documented migration path, but the docs paragraph claims idempotence without flagging the silent-conflict edge.

## High-level view

The schema-split decision is the right one and is now documented end-to-end: each Qdrant collection has its own internally-consistent name (`metadata.furnished` for document/CSV, top-level `is_furnished` for apartments). No attempt is made to unify the names across collections — the right call given how deeply `is_furnished` is wired into the apartments dialog and tooling.

The runtime producer change is small and surgical. `FilterExtractor._extract_furniture` is renamed to `_extract_furnished` and now returns `True | False | None`; the dict key `"furnished"` is what `_build_filter` prefixes to `metadata.furnished`. Negative patterns are checked before positives so the substring "мебел" inside "без мебели" cannot regress to a positive match. The `query_filter_signal` change is purely cosmetic — only the reason label moves from `"furniture"` to `"furnished"`; the regex `_FURNITURE_RE` is unchanged.

The most subtle behavioral question is what happens to LLM-driven filters. `QueryAnalyzer` is currently dormant in production (no instantiation in `bot.py` — `_extract_pre_agent_filters` uses the regex `FilterExtractor` only), but the prompt is meant to be live behavior. Because `QueryAnalysisResult.filters` is `dict[str, Any]`, an LLM that types `"true"` instead of `true` produces a string against a BOOL index and zero-matches silently. Under the old keyword scheme the same drift would still match — this is a tightening *and* a brittleness introduced by the PR.

The migration story rests on a verifiable claim: the chunker has always written `furnished` (bool) and never written `furniture`, so the legacy `metadata.furniture` KEYWORD index has zero data hits and no payload backfill is required. Confirmed at `src/ingestion/chunker.py:335` (`"Мебель": "furnished"`) and `src/ingestion/indexer.py:229` (`for field in ["furnished", "year_round"]: ... PayloadSchemaType.BOOL`). The script is idempotent for the *documented* path but its `"already exists, skipping"` branch swallows any error containing that substring without inspecting the existing field's schema, which the docs paragraph does not call out.

The two new test files are well-shaped. `test_setup_qdrant_indexes.py` mirrors the harness in `tests/unit/scripts/test_apartments_setup_collection.py` (mock the I/O boundary, call the production function, inspect `create_payload_index.call_args_list`). `test_query_analyzer_prompt.py` pins the SYSTEM_PROMPT contract.

Mitigated in the live path because the regex extractor runs ahead of any LLM, but the prompt example should list both forms for clarity.

### Bool flow through `_build_filter`

The PR relies on `_build_filter` discriminating with `isinstance(value, dict)` (not `int`), so bools fall through to the exact-match branch. Verified live:

```
_build_filter({'furnished': True})
  → must=[FieldCondition(key='metadata.furnished',
                         match=MatchValue(value=True))]
_build_filter({'furnished': False})
  → must=[FieldCondition(key='metadata.furnished',
                         match=MatchValue(value=False))]
```

The `isinstance(True, int) is True` Python gotcha cited in the spec does not bite here because the discriminator is `dict`, not `int`.

### Negative-pattern ordering in `_extract_furnished`

```
_extract_furnished("квартира без мебели")     → False
_extract_furnished("немеблированная студия")  → False
_extract_furnished("обставленная квартира")   → True
_extract_furnished("квартира с мебелью")      → True
_extract_furnished("квартира в Варне")        → None
```

`None` is the new "not mentioned" signal; the caller's guard had to change from `if furniture:` to `if furnished is not None:` since `False` is now a meaningful filter value the previous truthiness check would have dropped.

### LLM-side type drift on `furnished`

When `QueryAnalyzer` is wired in, an LLM emitting `"furnished": "true"` (a plausible failure mode if the prompt drifts or if the model is swapped) passes through `_build_filter` as `MatchValue(value="true")` against a BOOL index and silently returns zero matches. This is strictly worse than the pre-PR keyword scheme where any string was a valid match-target. A single-line sanitizer at the boundary — coerce `furnished` and `year_round` to bool, drop the key on failure — would close this without changing the prompt contract.

### Langfuse fallback caveat

`QueryAnalyzer.analyze` (line 138) loads the active prompt with `get_prompt_with_object("query-analysis", fallback=SYSTEM_PROMPT)`. SYSTEM_PROMPT is the *fallback* — used only when Langfuse is unavailable or returns nothing. The PR does not modify the Langfuse-stored entry. If the live `query-analysis` prompt in Langfuse still contains the legacy `furniture (string): "Есть"` instruction, deploying this PR alone leaves the LLM emitting the old key in production. `test_query_analyzer_prompt.py` guards the fallback constant only, so the test suite cannot detect the live-prompt drift.

### `already exists, skipping` and the migration claim

```python
except Exception as e:
    if "already exists" in str(e).lower():
        print("ℹ️  Index already exists, skipping")
        success_count += 1
    else:
        print(f"❌ Error: {e}")
```

The branch swallows any exception whose message contains the substring `already exists`, regardless of whether the existing index has the schema the script intended to create. For the *documented* migration path this is benign — the chunker has never written `furniture`, so a deployment with the legacy `metadata.furniture` KEYWORD index has zero data on that field, and the new BOOL index `metadata.furnished` is created cleanly alongside it. But the docs claim "Re-running ... is idempotent: it logs 'Index already exists, skipping' for pre-existing fields" is true only if the existing field already has the same schema. Tighten the script (read back the schema and compare) or add a one-line caveat to the migration paragraph.

### Test harness and coverage

`test_setup_qdrant_indexes.py` adapts the apartments harness for the entry-point shape difference: the apartments script takes the client as an argument (`create_payload_indexes(mock_client)`), whereas `setup_indexes()` reads it from `BotConfig` and instantiates `QdrantClient` internally — so this test patches both `telegram_bot.setup_qdrant_indexes.QdrantClient` and `telegram_bot.setup_qdrant_indexes.BotConfig` at the module under test. Both assertions inspect `create_payload_index.call_args_list`: one positively pins `metadata.furnished` to `models.PayloadSchemaType.BOOL`, the other negatively asserts `metadata.furniture` is absent.

**Not tested:**
- The end-to-end flow `_extract_furnished → extract_filters → _build_filter` is not asserted in a single test. The bool round-trip was verified by hand in this review but no regression guard catches a future change to `_build_filter` that would route bools through the dict branch (e.g., an `isinstance(value, (dict, bool))` typo).
- The `already exists, skipping` branch in `setup_qdrant_indexes.py` is not exercised. A test that throws a fake `"index already exists"` exception from `create_payload_index` and asserts `success_count` advances would pin the script's idempotence contract.
- LLM-side type drift (string `"true"` vs bool `True`) is not exercised. If a sanitizer is added per issue #2, a test should pin its coercion contract.

### Caller chain

`rg -n '_extract_furniture' telegram_bot src tests` returns zero hits — the rename is complete with no orphaned callers. `rg -n '"furniture"' telegram_bot src` (excluding `.venv`) returns only the regression-guard test that asserts the legacy index is *not* created and the migration note in `docs/QDRANT_STACK.md`. `telegram_bot/services/search_event_store.py` continues to use the apartments-lane key `is_furnished` and is unaffected.
