# PropertyBot unit test coverage for core handlers

Four new test files (1,689 lines, 72 tests) cover the PropertyBot class init/start lifecycle, menu button routing, query supervisor phases (content filter, semantic cache, handoff mode), feedback handling, and HITL callback flow. The tests use a consistent `_create_bot` factory that patches all heavy integrations (LLM, Qdrant, embeddings, cache, Redis) and exercises the real dispatch logic rather than just asserting mocks were wired. Watch for: duplicated helper scaffolding across all four files (confirmed); heavy mock-patching depth in query supervisor tests makes them fragile to internal refactors (likely); no negative-path coverage for `_send_markdown_chunks` failures or agent invocation exceptions within `_handle_query_supervisor` (confirmed).

## High-level view

The initialization tests cover attribute presence after `__init__` and verify `start()` sets up checkpointers, handles Redis failures by falling back to in-memory, and propagates preflight errors.

Menu routing tests validate that `handle_menu_button` dispatches to the correct `_handle_*` method based on `parse_menu_button` return values, including FSM state clearing for phone-collection flows. Service and CTA callback tests cover the parse-then-dispatch pattern with edge cases (unparseable data, missing forum bridge). The apartment fast-path tests cover the confidence threshold gate, escalation check, and successful end-to-end formatting.

Query supervisor tests exercise the three main gates before agent invocation: content filter (hard block, soft passthrough, disabled skip), semantic cache (hit returns early, miss invokes agent, non-cacheable type skips entirely), and handoff mode (full relay, relay-and-continue, no handoff). These are the highest-value tests in the set since `_handle_query_supervisor` is a ~1300-line method with many branches.

Feedback and HITL tests cover both the new `FeedbackCB` callback-data path and the legacy `fb:` string format, plus the approve/cancel flows in `handle_hitl_callback`.

## Duplicated test scaffolding

All four files define identical `_make_config` and nearly identical `_create_bot` helpers. The only variation is that `test_bot_initialization.py` adds `manager_ids=[123]` and `test_bot_query_supervisor.py` adds `content_filter_enabled=True, guard_mode="hard"` to the defaults. If `BotConfig` ever gains a new required field, all four helpers break independently. A shared fixture (either via `conftest.py` or a literal import) would eliminate this.

The `_start_patches` helper in `test_bot_initialization.py` uses `ExitStack` to assemble 16 patches. Any change to `start()` that adds a new external call will require updating this helper, making these tests fail without indicating a behavioral regression.

## Query supervisor mock depth and brittleness

The semantic cache tests require patching `classify_query`, `propagate_attributes`, `get_client`, `write_langfuse_scores`, `score`, `_get_or_compute_pre_agent_dense`, `create_bot_agent`, `create_callback_handler`, `get_query_topic_hint`, `get_grounding_mode`, `detect_filter_sensitive_query`, `is_contextual_query`, and `resolve_semantic_cache_signature`. That's 13 patches for a single test case. The coupling to internal structure is extreme -- any extraction of a helper function or module rename breaks these tests without indicating real behavioral change.

The `propagate_attributes` mock pattern (`mock_prop.return_value.__enter__ = MagicMock(...)`) is repeated in every supervisor test. If `propagate_attributes` ever migrates from synchronous to async context manager protocol, every test breaks silently (enters the mock but doesn't actually propagate context).

## Coverage gaps

Methods **not tested** in this batch despite being named in the issue (#1088):

- `handle_voice` edge cases (mentioned in the issue description but absent from test files)
- `handle_feedback_reason` (the follow-up after dislike keyboard is shown)
- Agent invocation failure path in `_handle_query_supervisor` (the `except Exception` branch that sends a fallback message)
- `_handle_apartment_fast_path` with `state` parameter updating catalog state (mentioned in FEAT-003 steps but the test doesn't pass a state object)

## Style inconsistency

`test_bot_menu_routing.py` uses explicit `@pytest.mark.asyncio()` decorators while the other three files rely on pytest-asyncio's auto mode. The tests work either way, but this divergence will confuse contributors about which pattern is canonical.
