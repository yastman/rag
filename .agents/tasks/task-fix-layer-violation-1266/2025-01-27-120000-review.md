# Layer violation fix: extracting shared code from telegram_bot/ to src/

The `src/` domain layer imported observability, service clients (BGE-M3, Voyage), retry utilities, and data models (apartment) from `telegram_bot/` — a transport layer. This change moves the shared code into `src/` and converts the original `telegram_bot/` files into thin re-export wrappers, preserving backward compatibility for all existing `telegram_bot/` consumers. Tests are updated to patch at the new canonical module paths.

**Watch for:** The `create_callback_handler` function accesses `_LANGFUSE_AVAILABLE` via a deferred import from `src.observability` but uses the top-level-bound `get_langfuse_client` (confirmed) — an asymmetry that creates a stale-binding trap if modules are reloaded independently. The hardcoded `"telegram-bot"` OTEL service name now lives in the domain layer where non-bot consumers will inherit it (confirmed).

## High-level view

The extraction follows a uniform pattern: full module content moves into `src/`, internal imports are retargetted from `telegram_bot.*` to `src.*`, and the original `telegram_bot/` file is gutted to a re-export stub with an `__all__` that matches the original public surface. Re-exports mean no downstream breakage and zero coordination cost with the rest of the `telegram_bot/` codebase.

One function, `create_callback_handler`, stays in `telegram_bot/observability.py` because it depends on `langfuse.langchain` (a LangChain-specific integration appropriate to the transport layer). It reaches back into `src.observability` for `_LANGFUSE_AVAILABLE` and uses the re-exported `get_langfuse_client`, creating a binding asymmetry between import-time and call-time resolution.

Six `from telegram_bot` imports remain in `src/api/main.py` — all for graph, cache, scoring, and state concerns that are explicitly out of scope for this extraction.

<summary>Issues (3)</summary>

1. **Stale binding risk in `create_callback_handler`** — The function imports `_LANGFUSE_AVAILABLE` at call time from `src.observability` but uses the top-level-imported `get_langfuse_client` binding. If `src.observability` is reloaded (as tests do), `get_langfuse_client` may reference an outdated module state. Consider importing `get_langfuse_client` inside the function body alongside `_LANGFUSE_AVAILABLE`.
2. **Hardcoded `"telegram-bot"` service name in src/ module** — `_ensure_otel_service_name("telegram-bot")` is called inside `src/observability.py`. Now that this module is the domain-layer canonical location, the default service name should arguably be layer-neutral or configurable so non-bot consumers (ingestion workers, API) don't report as "telegram-bot".
3. **Missing `__all__` in `src/observability.py`** — The module exports many public and semi-private names but lacks an `__all__`, making it unclear which symbols are part of the stable interface versus internal helpers. Any `from src.observability import *` consumer would get everything including `_pii_redactor`, `_langfuse_client`, etc.

## `create_callback_handler` coupling

`telegram_bot/observability.py` re-exports `get_langfuse_client` from `src.observability` at the module top level. But `create_callback_handler` (which remains in this wrapper) does a deferred `from src.observability import _LANGFUSE_AVAILABLE` inside its body. One dependency is resolved at import time (binding snapshot), the other at call time (fresh lookup). Any future test that reimports only `src.observability` without also reimporting `telegram_bot.observability` will get a stale `get_langfuse_client` in the wrapper.

```python
# telegram_bot/observability.py — current
from src.observability import get_langfuse_client  # bound at import

def create_callback_handler(...):
    from src.observability import _LANGFUSE_AVAILABLE  # fresh at call time
    if not _LANGFUSE_AVAILABLE:
        return None
    if get_langfuse_client() is None:  # uses top-level binding
        ...
```

Confidence: **likely** — not a bug today but a maintenance trap.

## Service name leak across layers

`src/observability.py` calls `_ensure_otel_service_name("telegram-bot")` during `initialize_langfuse()`. Now that this module is the domain-layer canonical location, any service that calls `initialize_langfuse()` — including the FastAPI app and ingestion workers — will default to reporting as "telegram-bot" in OpenTelemetry traces unless `OTEL_SERVICE_NAME` is explicitly set. The test `test_initialize_langfuse_sets_otel_service_name_when_absent` asserts this value, so it's an intentional carry-forward, but it's tech debt worth tracking.

Confidence: **confirmed**.

## Re-export completeness

The `telegram_bot/observability.py` wrapper does not re-export `_LANGFUSE_AVAILABLE`, `Langfuse`, `_LANGFUSE_IMPORT_ERROR`, `_resolve_config_value`, or other internal names that external code might have accessed directly from the old `telegram_bot.observability`. Any such consumer would break silently. Given the convention of underscore-prefixed names being internal this is likely acceptable, but worth a grep through the broader codebase if there are other repos consuming `telegram_bot` as a library.

Confidence: **possible**.
