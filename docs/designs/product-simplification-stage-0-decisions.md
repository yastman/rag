# Решения Этапа 0: Фиксация Направления Упрощения

Статус: предлагается
Дата: 2026-06-03
Источник плана: [`product-simplification-e2e-plan.md`](product-simplification-e2e-plan.md)

## Цель Этапа 0

Зафиксировать продуктовое направление, архитектурные решения и границы до
начала какой-либо работы с кодом. Никаких изменений выполнения или удалений
на этом этапе.

## Что Строим

> Доменный ассистент, который отвечает по приватной базе знаний и выполняет
> CRM- и рабочие действия только после подтверждения человеком.

Целевой продуктовый путь:

```text
намерение пользователя
  -> единый процесс основного ассистента
  -> реальный поиск по тестовым документам
  -> реальный ответ LLM
  -> опциональное CRM-действие с подтверждением человеком
  -> простые структурированные логи
```

Основные компоненты:

- **Монолитное ядро ассистента** в одном Python-процессе.
- **Текстовый Telegram-ассистент** как основной продакшен-канал.
- **Путь RAG-запроса**: классификация намерения, поиск в Qdrant, эмбеддинги
  внутри процесса, генерация через LLM, подготовка CRM-действия.
- **Qdrant** как главная обязательная внешняя зависимость.
- **BGE-M3 или другой путь эмбеддингов внутри процесса** — без обязательного
  отдельного API-контейнера.
- **Docling для индексации внутри процесса** — без постоянно запущенного
  сервиса.
- **LiteLLM как Python-зависимость или прямой SDK провайдера** — без
  обязательного прокси-контейнера.
- **Реальная генерация через LLM**.
- **CRM/HITL как возможность продукта** — с моком CRM в E2E.
- **Структурированные логи в JSON** — основной механизм отладки и
  наблюдаемости.

## Что Не Строим (Неосновное)

Эти поверхности **не удаляются** на Этапе 0 и далее не удаляются без
явного решения Артёма. Они помечаются как опциональные или будущие
опциональные:

- Голосовой режим LiveKit.
- Мини-приложение.
- Отдельный API для RAG (если нет реального потребителя).
- BGE-M3 API-контейнер как обязательная сервисная граница.
- Постоянно запущенный Docling-сервис.
- LiteLLM прокси-контейнер как обязательная среда выполнения.
- Langfuse как обязательная среда выполнения, CI-шлюз или доказательство
  корректности.
- Самостоятельно развёрнутый стек Langfuse как обязательный локальный запуск.
- Loki, Promtail и Alertmanager как обязательный локальный запуск.
- Kubernetes-манифесты как обязательная поверхность проверки.
- Исчерпывающие контракты трассировки и реестры спанов.

## Принятые Решения

### Решение 1: Монолитное Ядро

**Что:** Архитектура ядра движется к монолиту — один Python-процесс и
явные внешние клиенты.

**Форма:**

```text
Telegram-адаптер или тестовый E2E-вызов
  -> Python-модуль основного ассистента
       -> клиент Qdrant
       -> модуль эмбеддингов внутри процесса
       -> парсинг и нарезка документов внутри процесса
       -> LiteLLM или прямой LLM-клиент
       -> CRM-клиент
```

**Почему:** Каждая новая поверхность выполнения добавляла сетевую границу.
Каждая граница требовала трассировки, проверки здоровья, контрактов и
защитных проверок. Монолитное ядро разрывает этот цикл.

**Что меняется:** Внутренние HTTP-границы заменяются границами
Python-модулей и функций. Сетевые границы остаются только для настоящих
внешних зависимостей.

### Решение 2: Langfuse Опционален

**Что:** Langfuse не входит в основной продуктовый путь.

**Правила:**

- Бот должен запускаться без Langfuse.
- `make e2e-core-live` должен проходить без Langfuse.
- Отсутствие доступов к Langfuse не должно ломать основной запуск.
- Langfuse не должен быть обязательным CI- или релизным шлюзом.
- Если Langfuse включён, он пишет диагностику и не меняет поведение продукта.

**Когда вернуть:** Langfuse можно вернуть как опциональную возможность при
конкретной потребности: сравнивать промпты и модели, смотреть реальные
продакшен-диалоги, считать стоимость и задержку LLM.

### Решение 3: Распределённая Трассировка Не Требуется

**Что:** Распределённая трассировка (OpenTelemetry) не является обязательным
механизмом проверки корректности для упрощённого ядра.

**Целевое состояние:**

```text
Надёжность ядра:
  живой E2E + структурированные логи

Опциональная диагностика:
  Langfuse / OTel / дымовая проверка трассировки
```

**Что не делаем:** Не удаляем код трассировки на этом этапе. Контракты
трассировки сокращаются только после стабилизации живого E2E золотого пути.

### Решение 4: Telegram Как Продакшен-Адаптер

**Что:** Telegram остаётся продакшен-адаптером, но не обязан быть частью
главного E2E-шлюза надёжности.

**Почему:** Корректность продукта принадлежит E2E-набору ядра ассистента.
Ошибки транспорта должны ловиться маленькой дымовой проверкой адаптера.

**Форма:** Telegram-адаптер принимает сообщения, вызывает единую точку входа
ядра и отображает `AssistantResult`.

### Решение 5: CRM С Моком В E2E

**Что:** CRM остаётся частью продукта, но E2E использует мок или тестовый
сервер CRM.

**Правила:** Не трогать реальные пути записи в CRM в тестах. Подтверждение
человеком требуется перед любой записью.

### Решение 6: Наблюдаемость Через Структурированные Логи

**Что:** Основным механизмом наблюдаемости становятся структурированные
JSON-логи через стандартный Python `logging` с обёрткой `log_event(...)`.

**Обязательные события:** запрос начат, поиск завершён, LLM завершил работу,
CRM-действие предложено, CRM-действие подтверждено, зависимость отказала.

**Обязательные поля:** `event`, `request_id`, `route` или `request_type`,
`latency_ms` для завершённых этапов, `error_type` для ошибок.

## Неосновные Поверхности, Которые Пока Не Удаляем

| Поверхность | Статус | Причина |
|---|---|---|
| Голосовой режим LiveKit | Помечен как опциональный | Может быть активным пользователем |
| Мини-приложение | Помечен как опциональный | Может быть активным пользователем |
| Отдельный API для RAG | Помечен как опциональный | Нет подтверждённого потребителя |
| BGE-M3 API-контейнер | Помечен как опциональный | Эмбеддинги переходят внутрь процесса |
| Docling-сервис | Помечен как опциональный | Индексация переходит внутрь процесса или пакетный запуск |
| LiteLLM прокси-контейнер | Помечен как опциональный | Остаётся Python-зависимостью |
| Langfuse (весь стек) | Помечен как опциональный | Не является обязательным шлюзом |
| Loki, Promtail, Alertmanager | Помечен как опциональный | Не нужны для упрощённого ядра |
| k8s-манифесты | Помечен как опциональный | Не обязательная поверхность проверки |
| Контракты трассировки | Помечен как опциональный | Будет сокращён после E2E золотого пути |

## Открытые Вопросы Для Артёма

Эти вопросы требуют явного решения Артёма до или во время Этапа 1:

1. **Подтверждение направления монолитного ядра.** Согласен ли Артём с тем,
   что архитектура движется к одному Python-процессу с явными клиентами, а
   не к распределённой платформе?

2. **Судьба опциональных поверхностей.** Какие из неосновных поверхностей
   (LiveKit, мини-приложение, API для RAG) имеют активных пользователей и
   должны сохраняться в рабочем состоянии, а какие можно архивировать?

3. **Выбор LLM-провайдера для E2E.** Какой LLM использовать для живого E2E:
   GPT-4o-mini, локальную модель или другой вариант? Важны стоимость,
   стабильность и доступность.

4. **Бюджет на живой E2E.** Есть ли ограничение на количество вызовов LLM
   в CI/ночном прогоне?

5. **CRM-окружение для тестов.** Использовать ли существующий тестовый
   сервер CRM или нужен отдельный мок?

6. **Сроки интеграции `simplification/core` в `dev`.** Когда планируется
   первый мерж недельного пакета изменений в `dev`?

7. **Приоритет этапов.** Правильный ли порядок этапов? Нужно ли ускорить
   какой-либо этап или отложить?

## Границы Первой Недели

Из [`yaroslav-simplification-workflow.md`](yaroslav-simplification-workflow.md):

**Разрешено на первой неделе:**

- Краткое объяснение понимания плана.
- Сводка принятых решений (этот документ).
- Корпус тестовых данных.
- Эталонные сценарии (`golden_cases.yaml`).
- Помощник Qdrant для E2E.
- Помощник логирования (`log_event`).
- Тесты помощников без сервисов.
- Дизайн-документы и планы.

**Запрещено на первой неделе:**

- Удалять код.
- Менять запуск.
- Менять поведение CRM.
- Менять поведение Langfuse.
- Заменять пути BGE-M3, Docling или LiteLLM.
- Писать полный E2E-набор до одного E2E золотого пути.

**Цель первой недели:** сделать следующую архитектурную работу безопаснее,
а не упростить архитектуру сразу.
