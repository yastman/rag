# Процесс Работы С Ярославом По Упрощению Проекта

Статус: предлагается
Дата: 2026-06-02
Связанный план: [`product-simplification-e2e-plan.md`](product-simplification-e2e-plan.md)

## Цель Процесса

Дать Ярославу возможность быстро работать с помощью вайб-кодинга, но защитить `dev` и архитектурное направление проекта.

Главная идея:

```text
Ярослав сам изучает следующий этап и предлагает задачи.
Артём утверждает только направление, решения, требующие его участия, и недельный пакет изменений.
```

Это не процесс постоянного микроменеджмента. Это две точки контроля в неделю.

## Базовая Модель

```text
docs/designs/product-simplification-e2e-plan.md
  -> Ярослав изучает следующий этап
  -> Ярослав формирует свое понимание и список задач
  -> Артём утверждает или правит задачи недели
  -> Ярослав делает маленькие запросы на слияние
  -> запросы на слияние идут в simplification/core
  -> в конце недели Артём принимает пакет изменений или блокирует его
```

## Ветки

```text
dev
  <- недельный пакет изменений, только после утверждения Артёма

simplification/core
  <- интеграционная ветка для работы Ярослава

simplification/<номер-задачи>-<краткое-название>
  <- ветка одной задачи
```

Правила:

- Ярослав не мержит напрямую в `dev`.
- Каждая задача живет в отдельной ветке.
- запрос на слияние создается из ветки задачи в `simplification/core`.
- `simplification/core` может двигаться быстро, но `dev` остается защищенным.

## Две Точки Контроля В Неделю

### Точка 1: Планирование Этапа

Рекомендуемый слот: начало недели, 30-45 минут.

Ярослав заранее готовит `Предложение задач на неделю`.

Артём:

- проверяет, понял ли Ярослав этап;
- утверждает или сокращает предложенные задачи;
- отмечает задачи, требующие решения Артёма;
- запрещает опасные файлы или поверхности;
- задает фокус недели.

Результат:

- утвержденный список задач недели;
- список заблокированных вопросов;
- понятные границы работ.

### Точка 2: Приемка Недели

Рекомендуемый слот: конец недели, 60-90 минут.

Ярослав заранее готовит `Отчет приемки недели`.

Артём:

- смотрит сводку по недельному пакету, а не каждый запрос на слияние;
- принимает или блокирует решения, требующие участия Артёма;
- решает, можно ли мержить `simplification/core` в `dev`;
- формирует следующий этап или дает корректировки.

Результат:

- пакет изменений принят, заблокирован или принят частично;
- список исправлений;
- следующий фокус.

## Предложение Задач На Неделю

Файл или комментарий в GitHub-задаче перед первой точкой недели:

```md
# Предложение задач на неделю

Источник плана:
- docs/designs/product-simplification-e2e-plan.md

Целевой этап:
- Этап N: <название>

Мое понимание:
- <3-7 пунктов: что делаем и почему>

На этой неделе не делаем:
- <что явно не трогаем>

## Предложенные задачи

### TASK-001: <название>
Этап: <N>
Тип: механическая / ядро / требует решения Артёма
Ветка: simplification/<задача>-<кратко>
Требует решения Артёма: да/нет

Цель:
- <один результат>

Разрешенные файлы:
- <пути>

Запрещенные файлы или поверхности:
- <пути или системы>

Готово, когда:
- <наблюдаемые критерии завершения>

Проверка:
- <команды или доказательства>

Риск:
- низкий / средний / высокий
```

Артём отвечает коротко:

```text
Утверждаю TASK-001 и TASK-002.
Блокирую TASK-003: слишком рано, зависит от E2E золотого пути.
На этой неделе не трогать продакшен-записи в CRM и запуск Langfuse.
```

## Отчет Приемки Недели

Файл или комментарий в GitHub-задаче перед второй точкой недели:

```md
# Отчет приемки недели

Ветка:
- simplification/core

Диапазон:
- dev..simplification/core

## Выполненные задачи

- TASK-001: <сводка, ссылка на запрос на слияние>
- TASK-002: <сводка, ссылка на запрос на слияние>

## Проверки

- make check: прошло / упало / не запускалось
- точечные тесты: прошло / упало / не запускалось
- e2e-core-live: прошло / упало / не готово

## Доказательство продукта

Запрос:
- <запрос>

Найденные документы:
- <идентификаторы или названия>

Ответ:
- <короткий фрагмент или сводка>

Почему это доказывает этап:
- <один абзац>

## Решения Артёма

### D1: <вопрос>
Рекомендация:
- утвердить / отклонить / отложить

Почему:
- <короткое объяснение>

Риск:
- низкий / средний / высокий

## Рискованные изменения

- новые зависимости: нет / список
- новые сервисы: нет / список
- удаленные или архивированные поверхности: нет / список
- изменения поведения CRM: нет / список
- Langfuse/OTel стал обязательным путем: нет / да

## Запрос

Принять или заблокировать мерж:
- simplification/core -> dev до commit <sha>
```

## Типы Задач

В этом документе `требует решения Артёма` означает, что задачу нельзя мержить без явного решения Артёма.

### Тип 1: Механическая Задача

Примеры:

- документы;
- тестовые данные;
- `golden_cases.yaml`;
- вспомогательная обвязка тестовых помощников;
- тесты помощника логирования;
- отчеты только для чтения.

Можно мержить в `simplification/core` после проверок и агентского ревью.

### Тип 2: Задача Ядра

Примеры:

- единая точка входа ядра;
- интеграция помощника логирования;
- помощник Qdrant для E2E;
- первый E2E золотого пути.

Можно мержить в `simplification/core` только если задача явно разрешила затронутые файлы и проверки прошли.

### Тип 3: Требует Решения Артёма

Требует утверждения Артёма перед мержем:

- изменение поведения записи в CRM или HITL;
- удаление или архивирование поверхностей выполнения;
- превращение Langfuse или OTel в обязательный путь;
- удаление обязательных шлюзов трассировки;
- изменение API единой точки входа ядра после утверждения;
- добавление зависимости с влиянием на запуск;
- добавление любого сервиса или контейнера;
- изменение семантики релизных или CI-шлюзов.

## Жесткие Правила

Никогда без утверждения Артёма:

- мержить напрямую в `dev`;
- добавлять Docker-сервис или контейнер;
- создавать новую HTTP-сервисную границу;
- создавать параллельный RAG-конвейер;
- делать Langfuse или OTel обязательными;
- писать E2E через Telegram;
- трогать реальные записи в CRM в тестах;
- удалять голосовой режим, мини-приложение, API для RAG, Langfuse или код трассировки;
- расширять задачу за пределы утвержденной области;
- создавать запрос на слияние больше 500 строк или 10 файлов, кроме документации и тестовых данных.

Если есть сомнение:

- выбрать меньшую задачу;
- не удалять код;
- не добавлять сервисы;
- не менять поведение CRM;
- не делать опциональные системы обязательными;
- остановиться и спросить на ближайшей точке планирования или приемки.

## Запрос Для Агентского Ревью

Перед мержем запроса на слияние в `simplification/core` Ярослав просит агента сделать ревью с таким запросом:

```text
Проверь этот запрос на слияние против:
- docs/designs/product-simplification-e2e-plan.md
- docs/designs/yaroslav-simplification-workflow.md

Найди:
- выход за область утвержденной задачи;
- новый сервис или контейнер;
- новую HTTP-сервисную границу;
- параллельный RAG-конвейер;
- обязательный путь через Langfuse или OTel;
- Telegram в E2E;
- продакшен-записи в CRM в тестах;
- изменение поведения CRM или HITL;
- отсутствие request_id и структурированного логирования для новых продуктовых логов;
- слишком большой запрос на слияние для безопасного ревью.

Верни:
- ПРОШЛО / ЗАБЛОКИРОВАНО
- находки по убыванию серьезности
- команды, которые нужно прогнать перед мержем
```

Сводку агентского ревью нужно вставить в запрос на слияние.

## Недельный Бюджет Времени Артёма

Цель: около 2 часов в неделю.

Рекомендуемый ритм:

```text
Начало недели: 30-45 минут
  - прочитать предложение задач Ярослава
  - утвердить, переупорядочить или заблокировать задачи
  - задать запрещенные поверхности

Конец недели: 60-90 минут
  - прочитать отчет приемки недели
  - ответить на решения, требующие Артёма
  - принять или заблокировать мерж недельного пакета в dev
```

Артём не ревьюит каждый запрос на слияние, кроме задач, требующих решения Артёма.

## Первые Безопасные Недели

Первая неделя не должна включать рефакторинг выполнения.

Разрешено:

- краткое объяснение понимания плана;
- сводка принятых решений;
- корпус тестовых данных;
- эталонные сценарии;
- помощник Qdrant;
- помощник логирования;
- тесты помощников без сервисов.

Запрещено:

- удалять код;
- менять запуск;
- менять поведение CRM;
- менять поведение Langfuse;
- заменять пути BGE-M3, Docling или LiteLLM;
- писать полный E2E-набор до одного E2E золотого пути.

Цель первой недели: сделать следующую архитектурную работу безопаснее, а не упростить архитектуру сразу.
