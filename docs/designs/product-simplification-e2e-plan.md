# План упрощения продукта и живого E2E-покрытия

Статус: предлагается
Дата: 2026-06-02

## Краткое резюме

Проект нужно перевести от широкой платформы разговорного ИИ к одному понятному продуктовому пути:

```text
намерение пользователя
  -> единый процесс основного ассистента
  -> реальный поиск по тестовым документам
  -> реальный ответ LLM
  -> опциональное CRM-действие с подтверждением человеком
  -> простые структурированные логи
```

Главное архитектурное направление: **монолитное ядро вместо распределенной платформы**. Основной путь продукта должен выполняться в одном Python-процессе и обращаться к внешним зависимостям через явные клиенты. Распределенная трассировка не должна быть обязательным механизмом проверки корректности.

Telegram остается продакшен-адаптером, но не обязан быть частью главного E2E-шлюза надежности. Ядро продукта можно тестировать напрямую: реальный Qdrant, реальные эмбеддинги, реальная индексация, реальный LLM и мок CRM.

## Почему проект стал сложным

Сложность появилась не случайно. Проект одновременно пытался быть Telegram-ботом, API для RAG, голосовой средой LiveKit, мини-приложением, платформой индексации, локальным стеком ML-сервисов, платформой наблюдаемости и переиспользуемой платформой для портфолио.

Каждая новая поверхность выполнения добавляла сетевую границу. Каждая граница требовала трассировки, проверки здоровья, контрактов и защитных проверок. После очередного аудита появлялся новый контроль, и поверхность поддержки росла:

```text
платформенная поверхность
  -> распределенная граница
  -> требование трассировки или контракта
  -> находка аудита
  -> новая защитная проверка
  -> еще больше поддержки
```

Направление A разрывает этот цикл не за счет снижения качества, а за счет уменьшения числа обязательных поверхностей выполнения.

## Продукт Вместо Платформы

Репозиторий должен поставлять одну основную вещь:

> Доменный ассистент, который отвечает по приватной базе знаний и выполняет CRM- и рабочие действия только после подтверждения человеком.

Все остальное становится опциональным, экспериментальным или архивным. Платформенные возможности можно сохранить, но они больше не должны определять архитектуру, тестовую стратегию и релизный шлюз основного продукта.

## Целевая Архитектура

```text
Точка входа ассистента
  - Telegram-адаптер в продакшене
  - прямой Python-вызов в E2E

        |
        v

Основной конвейер ассистента
  - классифицировать намерение
  - достать контекст из Qdrant
  - посчитать эмбеддинги внутри процесса
  - сгенерировать ответ через LLM
  - подготовить CRM-действие при необходимости
  - потребовать подтверждение перед записью в CRM

        |
        +--> Qdrant, тестовая или продакшен-коллекция
        +--> BGE-M3 или модуль эмбеддингов внутри процесса
        +--> Docling как шаг индексации внутри процесса
        +--> LiteLLM как Python-зависимость или прямой SDK провайдера
        +--> Redis как опциональный кэш
        +--> Postgres как опциональное состояние
        +--> CRM-клиент в продакшене, мок CRM в E2E
```

Целевая форма не такая:

```text
бот -> API для RAG -> внутренний сервис -> стек трассировки
```

А такая:

```text
Telegram-адаптер или тестовый E2E-вызов
  -> Python-модуль основного ассистента
       -> клиент Qdrant
       -> модуль эмбеддингов внутри процесса
       -> парсинг и нарезка документов внутри процесса
       -> LiteLLM или прямой LLM-клиент
       -> CRM-клиент
```

Сетевые границы остаются только там, где это настоящие внешние зависимости. Внутренние границы должны быть границами Python-модулей и функций, а не HTTP-сервисами.

## Решения По Границам

- BGE-M3 и эмбеддинги остаются в основном Python-пути без обязательного отдельного API-контейнера.
- Docling используется как зависимость для индексации внутри процесса или пакетного запуска, а не как обязательный постоянно запущенный сервис.
- LiteLLM остается Python-зависимостью или тонким клиентским слоем, без обязательного прокси-контейнера в основном запуске.
- Telegram остается продакшен-адаптером: принимает сообщения, вызывает единую точку входа ядра и отображает `AssistantResult`.
- CRM остается частью продукта, но E2E использует мок или тестовый сервер CRM, чтобы не трогать реальные пути записи.
- Qdrant остается главной обязательной внешней инфраструктурной зависимостью.

## Основное И Неосновное

Основное:

- монолитное ядро ассистента в одном процессе;
- текстовый Telegram-ассистент как основной продакшен-канал;
- путь RAG-запроса;
- поиск в Qdrant;
- BGE-M3 или другой путь эмбеддингов внутри процесса;
- Docling для индексации внутри процесса или пакетного запуска;
- LiteLLM как Python-зависимость или прямой SDK провайдера;
- реальная генерация через LLM;
- индексация небольшого подготовленного набора документов;
- CRM/HITL как возможность продукта, но с моком CRM в E2E;
- структурированные логи с `request_id`, `user_id` или идентификатором тестового сценария, `route`, `latency_ms`, `retrieved_count`, `llm_model`, `error_type`.

Неосновное:

- голосовой режим LiveKit;
- мини-приложение;
- отдельный API для RAG, если нет реального потребителя;
- BGE-M3 API-контейнер как обязательная сервисная граница;
- постоянно запущенный Docling-сервис как обязательная среда выполнения;
- LiteLLM прокси-контейнер как обязательная среда выполнения;
- Langfuse как обязательная среда выполнения, CI-шлюз или доказательство корректности;
- самостоятельно развернутый стек Langfuse как обязательный локальный запуск;
- Loki, Promtail и Alertmanager как обязательный локальный запуск;
- Kubernetes-манифесты как обязательная поверхность проверки;
- исчерпывающие контракты трассировки и реестры спанов;
- большие защитные контракты, которые защищают внутреннюю архитектуру, а не видимое пользователю поведение.

Опционально позже:

- Langfuse для анализа промптов, моделей, стоимости и продакшен-диалогов, если появится реальная потребность;
- OpenTelemetry только как опциональная диагностика;
- дымовая проверка трассировки только для опциональных многосервисных поверхностей, если они снова станут основными.

## Что Мы Теряем

- Позиционирование как многоканальной платформы.
- Полноту распределенной трассировки через бота, API, голосовой режим, индексацию и внутренние сервисные границы.
- Историю переиспользуемой платформы, которую можно быстро адаптировать к любому домену.
- Часть продакшен-зрелости вокруг Langfuse и OTel-панелей.
- Уверенность, что каждая опциональная поверхность выполнения постоянно поддерживается.

## Что Мы Выигрываем

- Систему, которую новый сопровождающий может понять за один заход.
- Меньше обязательных сервисов для локальной разработки.
- Меньше ложных падений CI.
- Меньше волн аудита, которые порождают новую инфраструктуру аудита.
- Доказательство надежности, привязанное к пользовательским исходам.
- Более ясный README и демонстрационную историю.
- Более быстрые итерации по реальному продукту.

## Модель Надежности

Надежность должна доказываться живыми E2E-тестами продуктовых сценариев:

```text
тестовые документы
  -> реальная индексация
  -> реальная коллекция Qdrant
  -> реальный поиск
  -> реальный ответ LLM
  -> проверки по фактам, источникам и поведению при ошибках
```

Telegram намеренно исключается из главного E2E-шлюза. Ошибки транспорта должны ловиться маленькой дымовой проверкой адаптера. Корректность продукта принадлежит E2E-набору ядра ассистента.

## Набор Живых E2E-Тестов

Создать новый сфокусированный набор:

```text
tests/e2e_core/
  fixtures/docs/
    kvartiry.md
    uslugi.md
    ceny.md
    pravila.md
  golden_cases.yaml
  test_live_ingest_answer.py
  test_live_grounding.py
  test_live_error_paths.py
  test_live_crm_hitl.py
```

Тестовые данные:

- 5-10 маленьких синтетических документов без секретов и персональных данных;
- явные факты: объекты, цены, города, расстояния, правила, ограничения;
- области, которых намеренно нет в корпусе;
- один конфликтный случай, где похожие документы содержат разные факты.

`golden_cases.yaml` должен выражать продуктовые проверки, а не полный ожидаемый текст ответа:

```yaml
- id: beach_under_120k
  query: "Найди квартиру у моря до 120000"
  must_retrieve:
    - sunny_beach_studio
  must_contain:
    - "Sunny Beach"
    - "110000"
  must_not_contain:
    - "Mountain View Villa"
  answer_policy: grounded_answer

- id: missing_in_corpus
  query: "Найди замок в Софии с частным аэропортом"
  must_retrieve: []
  must_contain:
    - "не найдено"
  answer_policy: no_data_no_claim
```

Обязательные сценарии:

1. Индексация и ответ: создать уникальную коллекцию Qdrant, проиндексировать документы, выполнить реальный запрос, проверить найденные документы и обязательные факты.
2. Неизвестный вопрос: спросить о данных, которых нет в корпусе, и проверить, что ассистент не выдумывает ответ.
3. Поиск с фильтрами: запросить цену или локацию и проверить, что найденный контекст соответствует ограничениям.
4. Конфликт источников: проверить, что ответ использует правильный найденный документ.
5. CRM/HITL: запросить действие записи в CRM, проверить отсутствие записи до подтверждения, подтвердить действие и проверить один вызов мока CRM.
6. Отказ зависимости: симулировать таймаут LLM или ошибку CRM и проверить явный пользовательский ответ.

Реальные границы в E2E:

- Qdrant;
- путь эмбеддингов внутри процесса;
- Docling или парсинг документов внутри процесса;
- LLM-провайдер через LiteLLM или прямой SDK;
- код индексации;
- основной конвейер ассистента.

Подмененные границы:

- Telegram;
- запись в CRM;
- платежные и продакшен-поверхности записи.

## Команды E2E

Добавить одну основную команду:

```bash
make e2e-core-live
```

Ожидаемое поведение:

```text
1. Проверить обязательные переменные окружения и живые сервисы.
2. Создать изолированную коллекцию Qdrant: e2e_core_<timestamp>.
3. Проиндексировать тестовые документы.
4. Прогнать эталонные сценарии с реальным поиском и реальным LLM.
5. Прогнать CRM/HITL-сценарий против мока или тестовой CRM.
6. Напечатать компактный отчет: прошло или упало.
7. Удалить тестовую коллекцию, если E2E_KEEP_COLLECTION=1 не установлен.
```

Набор должен падать явно, если предусловия отсутствуют. Он не должен тихо пропускать основные сценарии в релизном шлюзе.

## Политика Шлюзов

Быстрый шлюз запросов на слияние:

- модульные тесты для основных функций;
- интеграционные тесты без сервисов;
- линт и проверка типов;
- без зависимости от живого LLM.

Предрелизный шлюз:

- `make e2e-core-live`.

Ночной шлюз:

- `make e2e-core-live`, если есть доступы и бюджет;
- иначе явный статус "не настроено", а не ложный зеленый результат.

Ручная дымовая проверка адаптера:

- один полный проход через Telegram, опционально;
- доказывает только подключение транспорта, не корректность продукта.

## Логирование И Наблюдаемость

После упрощения обязательной основой становятся структурированные логи, а не распределенная трассировка.

Логирование делается через стандартный Python `logging` в JSON-формате. Для продуктовых событий используется маленькая обертка `log_event(...)` над `logger.info(..., extra=...)`, чтобы не размазывать `extra={...}` по всем модулям.

Langfuse и OTel не участвуют в обязательном пути логирования.

Запрещенный стиль для событий ядра:

```python
logger.info("Получен запрос пользователя")
```

Целевой стиль:

```python
log_event(
    "assistant_request_completed",
    request_id=request_id,
    route=route,
    retrieved_doc_ids=retrieved_doc_ids,
    llm_model=model,
    latency_ms=latency_ms,
    error_type=None,
)
```

Пример JSON-события:

```json
{
  "event": "assistant_request_completed",
  "request_id": "e2e-beach-under-120k",
  "route": "rag_search",
  "retrieved_count": 3,
  "llm_model": "gpt-4o-mini",
  "latency_ms": 1840,
  "error_type": null
}
```

Минимально обязательные события:

- запрос начат;
- поиск завершен;
- LLM завершил работу;
- CRM-действие предложено;
- CRM-действие подтверждено;
- зависимость отказала.

Обязательные поля для продуктового события:

- `event`;
- `request_id`;
- `route` или `request_type`;
- `latency_ms` для завершенных этапов;
- `error_type` для ошибок;
- `retrieved_doc_ids` для событий поиска;
- `llm_model`, `input_tokens`, `output_tokens` для LLM-событий, если провайдер возвращает использование токенов.

Правила:

- каждый пользовательский или тестовый поток получает один `request_id`;
- E2E использует стабильный тестовый `request_id`, чтобы связать логи и артефакты;
- персональные данные и секреты не пишутся в логи;
- сырой промпт и сырой ответ можно сохранять только в E2E-артефактах или опциональной диагностике с явной политикой редактирования чувствительных данных;
- отсутствие JSON-форматтера считается ошибкой логирования.

Этого достаточно, чтобы отлаживать упрощенный продукт. Langfuse может оставаться опциональным инструментом глубокого анализа, но не должен определять корректность продукта.

## Политика Langfuse

Langfuse не входит в основной продуктовый путь.

Правила:

- бот должен запускаться без Langfuse;
- `make e2e-core-live` должен проходить без Langfuse;
- отсутствие доступов к Langfuse не должно ломать основной запуск;
- Langfuse не должен быть обязательным CI- или релизным шлюзом;
- проверка трассировки не должна блокировать поставку упрощенного ядра;
- если Langfuse включен, он пишет диагностику по возможности и не меняет поведение продукта.

Langfuse можно вернуть как опциональную возможность, когда есть конкретная потребность:

- сравнивать промпты и модели;
- смотреть реальные продакшен-диалоги;
- считать стоимость и задержку LLM по пользователям;
- диагностировать снова появившиеся многосервисные потоки.

До этого момента структурированные логи и живой E2E являются основным механизмом надежности.

## Сокращение Трассировки И Защитных Проверок

Не удалять все одним запросом на слияние. Сначала заменить страховку через единую точку входа ядра и золотой путь E2E, потом убирать старую обвязку.

Кандидаты на сокращение после стабилизации `e2e-core-live`:

- сжать `tests/observability/trace_contract.yaml` до короткой политики наблюдаемости или архивировать;
- заменить `scripts/validate_traces.py` меньшей проверкой, ориентированной на дымовой тест, или пометить ее опциональной;
- убрать шлюзы вида "каждый span должен быть описан в YAML";
- оставить только статические проверки подключения, которые предотвращают очевидно сломанную инструментацию, если Langfuse остается установлен;
- оставить `.github/bug-classes.yml` как память повторяющихся проблем, а не растущий каталог контрактов;
- убрать Langfuse и OTel из обязательного локального запуска и обязательного доказательства релиза.

Целевое состояние:

```text
Надежность ядра:
  живой E2E + структурированные логи

Опциональная диагностика:
  Langfuse / OTel / дымовая проверка трассировки
```

## Поэтапный План Реализации

Важный порядок: не начинать с удаления сервисов и не писать большой E2E-набор поверх старой платформенной архитектуры.

```text
1. Понять и зафиксировать план.
2. Подготовить тестовую и логирующую инфраструктуру.
3. Сделать одну защитную E2E-проверку золотого пути.
4. Только после этого поэтапно рефакторить архитектуру.
```

Первые этапы должны быть добавочными и обратимыми: документы, тестовые данные, помощники, обертка логирования, единая точка входа ядра без удаления старых путей. Удаления и перевод поверхностей выполнения в опциональный статус начинаются только после работающего живого E2E золотого пути.

### Этап 0: Изучить И Зафиксировать План

Результат:

- краткое объяснение для разработчика: что строим, что не строим, какие решения уже приняты;
- список открытых вопросов, которые требуют решения Артёма;
- список неосновных поверхностей, которые пока не удаляем, а только помечаем как будущие опциональные;
- явное решение, что архитектура ядра движется к монолиту: один Python-процесс и внешние клиенты;
- явное решение, что Langfuse опционален и не является релизным шлюзом;
- фиксация будущего продуктового направления без полного переписывания README на этом этапе.

Критерии приемки:

- Ярослав может объяснить план своими словами в недельном отчете;
- нет кода выполнения и удалений;
- каждая будущая обязательная проверка привязана к основному продуктовому пути;
- голосовой режим, мини-приложение, k8s и Langfuse явно помечены как опциональные, если нет текущего пользователя, который от них зависит;
- нет обязательного требования распределенной трассировки для упрощенного ядра.

### Этап 1: Подготовить Тестовую И Логирующую Инфраструктуру

Результат:

- синтетические документы в `tests/e2e_core/fixtures/docs/`;
- `golden_cases.yaml`;
- помощник для уникальных тестовых коллекций Qdrant;
- базовая обертка `log_event(...)` над Python `logging`;
- JSON-форматтер для продуктовых логов;
- структура E2E-артефактов, например `logs/e2e/<run_id>/`.

Критерии приемки:

- корпус тестовых данных не содержит чувствительных данных;
- ожидаемые факты явные и стабильные;
- помощник Qdrant создает уникальную коллекцию и умеет удалять ее по умолчанию;
- помощник логирования не зависит от Langfuse и OTel;
- нет изменений поведения продакшена, кроме безопасного добавления утилиты логирования.

### Этап 2: Создать Единую Точку Входа Ядра

Результат:

- маленькая точка входа, которая вызывает ассистента и RAG напрямую, без Telegram, API и голосового транспорта;
- форма результата, удобная для тестов: найденные документы, текст ответа, маршрут, ошибки, опциональное предложенное CRM-действие;
- минимальный структурированный контракт логов для основного пути.

Ориентир:

```text
run_assistant_request(
  query,
  collection,
  user_context,
) -> AssistantResult
```

Критерии приемки:

- единая точка входа переиспользует существующую бизнес-логику, а не строит параллельный RAG-конвейер;
- точка входа не требует Telegram, Telethon, мини-приложение, голосовой режим или Langfuse;
- старые точки входа могут продолжать работать через адаптеры.

### Этап 3: Сделать Один Живой E2E Золотого Пути

Результат:

- один живой E2E: документ -> индексация -> Qdrant -> единая точка входа ядра -> реальный LLM -> ответ по источникам;
- сохранение артефактов: запрос, найденные документы, ответ, результат проверки, релевантные структурированные логи;
- команда `make e2e-core-live` или временная точечная команда, если цель Makefile пока рано добавлять.

Критерии приемки:

- один тест золотого пути проходит против реального Qdrant и реального LLM;
- тест покрывает будущую упрощенную архитектуру, а не консервирует старую платформенную архитектуру;
- тест не использует Telegram и не трогает реальные пути записи в CRM;
- ошибка показывает понятную диагностику.

### Этап 4: Рефакторить Вокруг Защищенного Основного Пути

Результат:

- опциональные поверхности выполнения убраны из обязательного пути;
- обязательная проверка больше не зависит от голосового режима, мини-приложения, Langfuse и k8s;
- Telegram остается продакшен-адаптером, но не центром проверки надежности ядра;
- индексация становится понятным пакетным или CLI-путем для основного продукта;
- внутренние HTTP-границы заменяются границами Python-модулей и функций там, где нет реального внешнего потребителя.

Критерии приемки:

- E2E золотого пути продолжает проходить после каждого сокращения;
- каждая удаленная или опциональная поверхность явно отражена в документации или GitHub-задаче;
- нет нового параллельного RAG-конвейера;
- основной путь остается одно-процессным, кроме реальных внешних зависимостей.

### Этап 5: Расширить E2E-Набор Ядра

Результат:

- 5-6 тестов: индексация, ответ, неизвестный вопрос, фильтры, привязка к источникам, конфликт источников, CRM/HITL, отказ зависимости.

Критерии приемки:

- `make e2e-core-live` проходит против локальных сервисов;
- полный прогон достаточно маленький для использования перед релизом;
- проверки смотрят на найденные документы и обязательные факты, а не на точную прозу.

### Этап 6: Упростить CI И Локальную Проверку

Результат:

- шлюз запросов на слияние покрывает только быстрые проверки без сервисов;
- живой E2E становится предрелизной или ночной проверкой;
- опциональные поверхности убраны из обязательных шлюзов.

Критерии приемки:

- ни один обязательный шлюз не зависит от голосового режима, мини-приложения, Langfuse или k8s;
- отсутствие доступов для живого E2E падает явно, когда этот шлюз запрошен напрямую.

### Этап 7: Сократить Контракты Трассировки

Результат:

- проверка трассировки понижена до опциональной диагностики;
- большой реестр спанов больше не блокирует продуктовую работу;
- реестр классов ошибок остается только для повторяющихся реальных проблем;
- Langfuse и OTel не участвуют в обязательном запуске, `make e2e-core-live`, шлюзе запросов на слияние или релизном шлюзе.

Критерии приемки:

- надежность продукта покрывается `e2e-core-live`;
- оставшиеся проверки наблюдаемости короткие и проверяют только подключение;
- исчерпывающий YAML-каталог спанов больше не нужен для поставки основного продукта;
- отсутствие Langfuse не меняет видимое пользователю поведение.

### Этап 8: Переписать Документацию

Результат:

- README описывает упрощенный продукт;
- индекс документации разделяет документы основного продукта и архивные платформенные документы;
- руководство локальной разработки начинается с минимального основного пути.

Критерии приемки:

- новый участник может запустить основной продукт без чтения документов платформенной эпохи;
- опциональные системы имеют явные метки "не требуется для ядра".

## Риски Миграции

- Удаление платформенных гарантий может скрыть регрессии в опциональных поверхностях.
- Живой E2E с реальным LLM может быть нестабильным или стоить денег.
- Провайдеры LLM могут менять поведение.
- Старые документы и тесты могут продолжать подразумевать поддержку платформы, если их не почистить.
- Некоторые текущие пользователи могут зависеть от API, мини-приложения или голосовых путей.

Снижение рисков:

- явно пометить опциональные поверхности перед удалением тестов;
- делать LLM-проверки по фактам и правилам, а не по точному тексту;
- использовать температуру 0 и маленькие тестовые данные;
- запускать живой E2E перед релизом и ночью, а не на каждый маленький запрос на слияние;
- архивировать старые документы вместо тихого удаления операционного знания.

## Метрики Успеха

- Новый участник понимает архитектуру ядра меньше чем за 30 минут.
- `make e2e-core-live` доказывает реальный ответ по реальным проиндексированным данным.
- Основной продуктовый путь является одно-процессным, кроме реальных внешних клиентов.
- Обязательные проверки запросов на слияние быстрые и низкошумные.
- Количество строк контрактов трассировки и наблюдаемости существенно уменьшается.
- Langfuse опционален: его отсутствие не ломает запуск, E2E или релиз.
- Открытые GitHub-задачи смещаются от мета-защитных проверок к поведению продукта.
- README честно описывает проект как продукт, а не разросшуюся платформу.
